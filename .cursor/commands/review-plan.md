# /review-plan

Review a multi-phase implementation plan (the kind generated by
`/create-implementation-plan` or `/create-phase-chain`) against workspace
invariants and 12 architecture-soundness questions, before implementation begins.

This command is a **task adapter** for the architecture-handoff-protocol. The
shared rules govern the packet contract, dispatcher behavior, validation, and
closure:

- `architecture-handoff-protocol.mdc` — the six required packet blocks,
  validation contract, iteration & closure
- `projects/.cursor/rules/handoff-dispatchers.mdc` (workspaces sandbox) —
  capability matrix, dispatch shape, polling, failure handling
- `agent-skills/consult-routing.md` — transport axis (role-contract vs
  model-direct; ¬ MCP gate); `universal-llm-gateway/tmp/reviews/_handoff-packet-template.md`
  — six-block skeleton

`/review-plan` provides only the task adapter: plan discovery, the 12
architecture questions, corpus assembly, and the `Location:` field refinement
(`Phase:` + `Question:`).

## When to Use

- After drafting a multi-phase plan under `tmp/prompts/<name>/`, before
  implementation kickoff
- When iterating on a plan after applying first-pass review findings
- Complementary to `/consult-plan` (which scopes/refines) and `/diff-review`
  (which reviews the resulting code)

Unlike `/consult-plan --review` (hard-coded gap-analysis prompt) and
`/review-phase` (post-implementation spec fidelity), this command applies the
full handoff protocol to a design document.

## Invocation

```
/review-plan [mode] <plan-path>
```

`mode` — optional dispatcher name. Default: `web-claude`. Valid modes per
`projects/.cursor/rules/handoff-dispatchers.mdc`: `web-claude`, `team-reviewer [model]`, plus reserved
stubs (`openai`, `gemini`, `team:*`, raw model IDs) that stop with a guidance
message because plan reviews need live source-file access.

`plan-path` — required path to the plan directory under `tmp/prompts/` or to a
single phase markdown file.

| Argument | Effect |
|---|---|
| omitted or `web-claude` | `web-claude` dispatcher (default) |
| `team-reviewer` | `team-reviewer` dispatcher; model `openai/gpt-5.4` |
| `team-reviewer gemini` | `team-reviewer` dispatcher; model `google/gemini-3-pro-preview` |
| `team-reviewer <full-model-id>` | `team-reviewer` dispatcher; model as supplied |
| `openai` / `gemini` / `team:*` / `<full-model-id>` | reserved stub — stops with guidance |

Examples:

```
/review-plan tmp/prompts/coordination-overhaul
/review-plan web-claude tmp/prompts/coordination-overhaul
/review-plan team-reviewer tmp/prompts/coordination-overhaul
/review-plan team-reviewer gemini tmp/prompts/coordination-overhaul
/review-plan tmp/prompts/coordination-overhaul/phase2.md
```

## Instructions

### 0. Resolve Dispatcher and Plan Path

Parse args. Map `web-claude` and `team-reviewer [model]` per the table above.
Reserved stubs stop with: "Inline-only dispatch (no MCP tools) is reserved
for /review-plan. Plan reviews need live source-file access. Re-run with
`team-reviewer` or `web-claude`."

Report resolved dispatcher, model/agent, and plan path before proceeding.

### 1. Discover Plan Scope

Resolve `PLAN_PATH` to a concrete file set.

```bash
if [ -d "$PLAN_PATH" ]; then
    PLAN_DIR="$PLAN_PATH"
    PLAN_FILES=$(find "$PLAN_DIR" -maxdepth 1 -type f -name '*.md' | sort)
elif [ -f "$PLAN_PATH" ]; then
    PLAN_DIR=$(dirname "$PLAN_PATH")
    PLAN_FILES="$PLAN_PATH"
else
    stop and report: "$PLAN_PATH does not exist"
fi

# Subfolders (out-of-scope but mentioned in the packet's <excluded> block)
EXCLUDED_SUBDIRS=$(find "$PLAN_DIR" -maxdepth 1 -mindepth 1 -type d -printf '%f\n' 2>/dev/null)
```

Sort `PLAN_FILES` so README/OVERVIEW/index appears first if present, followed
by `phase1.md`, `phase2.md`, ... in numeric order, then any other top-level
markdown:

```bash
sort_key() {
    case "$(basename "$1" .md)" in
        README|OVERVIEW|index) echo "0_$1" ;;
        phase[0-9]*)
            n=$(basename "$1" .md | sed 's/[^0-9]*//g')
            printf '1_%03d_%s\n' "$n" "$1"
            ;;
        *) echo "2_$1" ;;
    esac
}
PLAN_FILES_SORTED=$(for f in $PLAN_FILES; do echo "$(sort_key "$f")|$f"; done | sort | cut -d'|' -f2)
```

Report: plan directory, file count + ordered list, total LOC, excluded
subdirs (with reason `generated-artifacts`).

**Stop if scope is empty**: "No top-level markdown files found under
`$PLAN_DIR`. Plan files should live at the directory root, not inside
`summaries/` or `reviews/`."

**If total LOC > 5000**: warn and offer to scope down to a phase subset.

### 2. Build the Packet

Materialize the six required blocks per `architecture-handoff-protocol.mdc`.

#### `<scope>` (task adapter)

```
Plan: <plan-name>
Plan dir: <plan-dir-relative-to-repo-root>
Files reviewed: <count>, <total LOC> lines
Excluded subdirs: <list with reason>
```

#### `<invariants>` (shared protocol template)

Extract per `architecture-handoff-protocol.mdc` § "Block 2": compose universal
parent-rule invariants (shared `libs/` primitives, transport, ModelId, events,
MCP relay, quality/scope) with loaded workspace `_ws.mdc` invariants
(topology, service lifecycle, API namespace, domain constraints).

#### `<task_guidance>` (task adapter — the 12 questions)

```
<task_guidance>
For each phase, evaluate against these 12 architecture-soundness questions.
Findings should reference the question number for traceability (e.g. "Phase 2
— Q9: ...").

1. PROBLEM FRAMING
   Is the problem grounded in observable failures (events, logs, user reports),
   or hypothetical? Cite evidence (observability queries, incident records).

2. SCOPE COUPLING
   Can each phase be implemented and shipped independently, or are phases
   silently coupled (later phase assumes mid-phase state of an earlier one)?
   Make implicit ordering explicit.

3. INVARIANT ALIGNMENT
   Does any proposed change conflict with the invariants block above? Quote
   the conflict and the specific invariant.

4. EXISTING PATTERN REUSE
   Does the plan reinvent infrastructure that already exists (transport
   helpers, event factories, model-id parsing, gateway/stargate abstractions)?
   Use rag/cortex/fs to verify before flagging.

5. NEW FAILURE MODES
   What failure modes does this introduce that did not exist before? Are
   they handled, observable, and recoverable?

6. ROLLBACK / INCREMENTALITY
   Can each phase be reverted without breaking later phases or leaving the
   system in an inconsistent state? Is mid-phase abort safe?

7. OBSERVABILITY
   Are new signals or events specified for the new behavior? Do signal names
   match the workspace signal format? Are existing signals updated where the
   flow changes?

8. TESTABILITY
   How would you verify each phase succeeded without manual inspection? Are
   quality-gate hooks (compile, lint, contract tests) covered?

9. CONCURRENCY / ORDERING
   Are race conditions, initialization ordering, eviction races, or shutdown
   ordering addressed? Multi-process / multi-container concerns?

10. PUBLIC CONTRACT CHANGES
    Does the plan modify any externally-facing API, event contract, or CLI
    surface? Is migration / deprecation handled? Downstream consumers
    enumerated?

11. PERFORMANCE / RESOURCE BOUNDS
    What is the throughput, latency, or resource expectation? How is it
    bounded? What happens under sustained load?

12. CROSS-PHASE CONSISTENCY
    Do later phases depend on assumptions from earlier ones? Are those
    assumptions stated explicitly, or buried in implementation detail?

A clean phase passes all twelve.
</task_guidance>
```

#### `<corpus>` (task adapter — concatenated phase docs)

```bash
{
    for f in $PLAN_FILES_SORTED; do
        rel="${f#$PLAN_DIR/}"
        lines=$(wc -l < "$f")
        case "$(basename "$f" .md)" in
            README|OVERVIEW|index) role="overview" ;;
            phase[0-9]*)           role="phase" ;;
            *)                     role="supplementary" ;;
        esac
        echo ""
        echo "=== $rel ($lines lines, $role) ==="
        cat "$f"
    done
}
```

For `web-claude`: include the corpus only as a snapshot reference. The packet
body instructs the reviewer to re-read live files via `fs` before forming
findings. Do NOT instruct the reviewer to rely solely on the inlined corpus.

For `team-reviewer`: inline the full corpus — the model cannot read beyond
what is provided without a tool call.

#### `<mcp_capabilities>` (shared protocol template)

Use the dispatcher-flavored block from `projects/.cursor/rules/handoff-dispatchers.mdc` for the
chosen dispatcher (web-claude includes `agent_bus` + `<need>` last-resort;
team-reviewer omits both, makes Evidence inline mandatory).

#### `<output_format>` (shared template, task-flavored)

v1 structured shape per `architecture-handoff-protocol.mdc` § "Block 6:
`<output_format>`", with the plan-review adapter refinement: use `Phase:`
(README | phase1 | phase2 | ... | cross-phase) instead of `File:`, and
include the optional `Question:` field referencing Q1..Q12 or
invariant:<name>.

```
FindingID:    F<n>                              # stable, sequential
Severity:     Critical | Warning | Suggestion
Phase:        README | phase1 | phase2 | ... | cross-phase
Question:     Q1..Q12 | invariant:<name>       # optional
FileReadVia:  fs | absolute | not_read
Concern:      <one paragraph; cite invariant tag if applicable>
Evidence:     <MCP tool calls and what they returned>   # required if dispatcher has MCP
Operation:    replace | create_file | delete_file | delete_substring |
              replace_whole_file | replace_all_occurrences |
              plan_required | needs_info | deferred | blocked
DependsOn:    F<m>[resolved | applied | approach=A]   # semantic only
```

For mechanical Operations: include an Edits block (column-0 SEARCH/REPLACE
fences, Occurrence=exactly_once, ApplyAfter) and a Verify list (commands
from the closed Verify Allowlist per protocol § "v1 Dispatcher Apply
Contract"). For paused Operations: include required subfields per protocol
§ "Paused operations" (plan_required → Scope/MinimalPlan/AcceptanceChecks;
needs_info → WouldFetch or Questions; deferred → Options ≥2;
blocked → BlockedReason + UnblockedBy).

Reviewer MUST NOT emit: NewlineMode, FileSha256Before, ExpectedCount.

Return ONLY findings. If nothing found, return exactly: "No findings."

### 3. Write Packet

```
PLAN_NAME=$(basename "$PLAN_DIR")
PACKET="$PLAN_DIR/reviews/${DISPATCHER}-architecture-packet.md"
mkdir -p "$PLAN_DIR/reviews"
```

Write the materialized six-block packet to `PACKET`.

For `team-reviewer`: also set the system prompt partition (role + invariants +
mcp_capabilities + output_format) and the user message (corpus + scope metadata)
separately, per `projects/.cursor/rules/handoff-dispatchers.mdc` § "team-reviewer" partition.

Report: packet path written.

### 4. Dispatch

#### `web-claude`

**CRITICAL — `agent_bus` is a table of contents, NOT a content carrier.**

The packet (all six blocks) lives in the workspace file written in step 3.
The thread body MUST be ≤25 lines — a pointer and a one-sentence instruction.
¬ inline packet blocks, invariants, the corpus, or the 12 questions in the
body. `agent_bus` will silently truncate or refuse large payloads; Claude
Web will see a partial message and abandon the review without warning.

The packet file written in step 3 is the source of truth. Then post this
pointer:

```python
SLUG = f"review-plan-{PLAN_NAME}"
THREAD_RESP = agent_bus(tool="post", arguments={
    "slug": SLUG,
    "to": "claude-web",
    "from_agent": "cursor",
    "subject": f"Plan architecture review — {PLAN_NAME}",
    "tags": [
        f"project:{REPO_NAME}",
        "type:review",
        "agent:claude-web",
        f"plan:{PLAN_NAME}",
    ],
    "body": <thread body — see template below>,
})
THREAD_ID = THREAD_RESP["thread"]["id"]
```

Thread body template (keep to this shape — no additions):

```
Plan architecture review — {PLAN_NAME}
Scope: {N} files, {total LOC} lines  Plan dir: {PLAN_DIR}

Read the packet:
  fs(sandbox="workspaces", op="read", path="universal-llm-gateway/{PACKET}")

The packet has the six protocol blocks (scope, invariants, task_guidance with
Q1–Q12, corpus snapshot, mcp_capabilities, output_format). Re-read each phase
file live via `fs` before forming findings — do not rely on the inlined
snapshot. Reply on this thread, referencing Phase and Q1–Q12.

Signed, (Cursor) Claude
```

Report to the user: thread ID, packet path, artifact path
(`<PLAN_DIR>/reviews/web-claude-architecture-summary.md`).

#### `team-reviewer`

```python
EXEC = team_dispatch(
    op="generate",
    role="reviewer",
    dispatch_thread_id=f"review-plan-{PLAN_NAME}",
    messages=[{"role": "user", "content": <user message — corpus + scope metadata>}],
    model=<resolved model or None>,  # default from reviewer role (openai/gpt-5.5)
    system=<system parameter — role + invariants + mcp_capabilities + output_format>,
    reasoning_effort="high",
    caller_agent="cursor",
    max_tool_turns=25,
)
EXEC_ID = EXEC["execution_id"]
```

Poll via `pipeline(op="result", execution_id=EXEC_ID, wait_seconds=60)`.
Re-poll up to 5 × 60s. Report `EXEC_ID` to the user after dispatch.

### 5. Reply Handling Loop

#### For `web-claude` — manual async workflow

After posting, stop and wait for Claude Web to reply. When the user signals a
reply has arrived, inspect it.

##### 5a. Check for `<need>` tags

Parse the reply for `<need>path</need>` tags. For each:
- Fetch the file via `fs(sandbox="workspaces", op="read", path="universal-llm-gateway/<path>")`
- Append fetched content under `=== ADDITIONAL (requested by reviewer) ===`
- Reply on the thread with the appended content

Max one `<need>` fetch round per pass.

##### 5b. Triage findings

Apply the validation contract from
`architecture-handoff-protocol.mdc` § "Validation Contract".

Five-bucket triage: Apply / Reject by rule / Escalate / Surface for triage / Defer.

Report: `{N} findings → {K} Critical, {L} Warning, {J} Suggestion →
{applied} applied, {rejected} rejected, {surfaced} surfaced, {pending} pending`.

List every rejected finding with the rule that overrides it. List every
surfaced finding with a one-line scope note.

##### 5c. Post pushback

Reply on the thread with the triage outcome. For findings that conflict with a
workspace rule, state the rule name and the concrete reason. For deferred
findings, state what is blocking.

##### 5d. Convergence check

Convergence signals (any one closes the loop):
- `No findings.`
- `Review complete.`
- `<plan> implementation-ready`
- Explicit user instruction to close

Stable disagreement is a valid terminal state — record it in the artifact and
surface to the user instead of forcing closure.

#### For `team-reviewer` — synchronous

After polling completes, go directly to step 5b. There is no `<need>` handling
or async reply loop for team-reviewer. For iteration: validate + apply findings,
then re-dispatch with a rebuilt user message that includes a `<prior_pass>` block
summarizing what was applied/rejected/surfaced.

### 6. Close and Audit

#### 6a. Documentation contract audit

Check event-contracts.md and relevant docs for any applied finding that changed
event signals, event payloads, event semantics, failure modes, API surfaces, or
other runtime/user-visible contracts. Update or record why no update is required.

```
## Documentation Contract Audit
- `docs/event-contracts.md`: updated | not needed: <reason>
- other docs: <paths> | not needed: <reason>
```

#### 6b. Close thread (`web-claude` only)

```python
agent_bus(tool="close", arguments={
    "thread": THREAD_ID,
    "summary": f"Plan review {PLAN_NAME}: {applied} applied, {rejected} rejected, {surfaced} surfaced",
})
```

#### 6c. Write artifact

Write to `<PLAN_DIR>/reviews/<dispatcher>-architecture-summary.md`:

```markdown
# Plan Review: {PLAN_NAME}

**Date**: {ISO-UTC}  **Dispatcher**: {dispatcher}  **Model/Agent**: {id}
**Plan dir**: {PLAN_DIR}  **Files**: {N}, {total LOC} lines
**Packet**: {PACKET}
**Thread**: {THREAD_ID}        # web-claude only
**Execution IDs**: {list}      # team-reviewer only

## Summary
{N} findings, {M} validated ({K} Critical, {L} Warning, {J} Suggestion)
→ {X} applied, {Y} rejected by rule, {Z} surfaced for triage, {W} pending

## Critical
{findings or "None"}

## Warnings
{findings or "None"}

## Suggestions
{findings or "None"}

## Applied
- phase{N} Q{M}: <description>
- (none)

## Rejected by Rules
- <finding> — overridden by `<rule-file>`: <reason>

## Surfaced for Triage
- <finding> — touches `<out-of-scope path>`: <scope note>

- other docs: <paths> | not needed: <reason>

- Convergence signal: `{signal}` at turn {N}
```

## Plan-Review Specifics

These are the only `/review-plan`-specific deviations from the protocol; all
else is shared.

- **Plan discovery sort order** (step 1) — README first, phases numerically,
  others last. Subdirs excluded.
- **5000 LOC warning gate** (step 1) — plan reviews can balloon with
  supplementary docs; offer phase-subset scoping.
- **12 architecture questions** (step 2 `<task_guidance>`) — the canonical
  evaluation criteria; reference by Q1..Q12 in findings.
- **`Phase:` + `Question:` location refinement** — supersedes the protocol's
  default `Location:` field.
- **Artifact location** under `<PLAN_DIR>/reviews/`, not `tmp/reviews/` —
  keeps the review next to the plan it reviewed.
- **Reserved stub modes** — inline-only generate (no MCP tools) is reserved for
  `/review-plan` because plan reviews need live source-file access.

## Rules

- ¬ proceed if `PLAN_PATH` is empty or contains no top-level markdown
- ¬ proceed past 5000 LOC without user confirmation
- ¬ skip the validation contract (`architecture-handoff-protocol.mdc`)
- ¬ run reserved stub modes — they stop with guidance
- ¬ apply any finding without showing it first
- ¬ close thread before a convergence signal or explicit user direction
- ¬ close without completing the documentation contract audit (step 6a)
- Agent bus thread state is the source of truth for `web-claude` review status
- Max one `<need>` fetch round per pass
- **`agent_bus` body is a table of contents only** — ≤25 lines, packet path
  pointer, no inlined content. All packet blocks (invariants, task_guidance,
  corpus, output format) live in the workspace packet file read via `fs`.
  Violating this causes silent truncation and Claude Web abandons the review.
- All other rules inherited from `architecture-handoff-protocol.mdc` and
  `projects/.cursor/rules/handoff-dispatchers.mdc`
